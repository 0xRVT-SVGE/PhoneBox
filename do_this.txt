Your current validation logic (ROI overlap + QR disappearance) is fragile for this scenario. It will fail exactly at the moment that matters: when the phone rotates and the visible features (QR + front face) disappear. You need continuity through appearance change + rotation, not just detection.

A robust solution is to treat this as a stateful tracking + event validation pipeline, not a single condition.

1) Core Problem Breakdown

You are dealing with:



* Rotation (≈90° flip) → appearance changes drastically

* Partial/temporary occlusion → QR disappears

* Final pose constraint → phone must end inside slot ROI in a specific orientation

A single tracker will not handle all of this reliably.

2) Recommended Architecture (Robust)

A. Dual-Mode Tracking (Do NOT rely on one method)

Phase 1 — After QR detection



* Initialize:

   * A tracker: CSRT or KCF (fast enough)

   * A feature model: ORB descriptors of the phone region

Why: Tracker gives smooth motion; ORB gives re-identification when rotation breaks the tracker.

B. Add Motion-Based Tracking (Critical)

When appearance breaks (rotation), switch to:



* Contour / blob tracking (largest moving object near last known position)

* Optical flow (e.g. Lucas-Kanade) on tracked keypoints

This ensures you never lose the object, even if it visually changes.

C. Re-detection Safety Net

Run a lightweight detector periodically:



* YOLO (even small model) every N frames

* Restrict search to region around last known position

This prevents permanent drift.

3) Orientation Awareness (You’re Missing This)

Right now, you're not actually validating rotation — only position.

You need to explicitly track orientation change.

Option 1 (Simple, effective)

Use OpenCV:



* `minAreaRect(contour)` → gives angle of rotated rectangle

Track:



* Initial angle (horizontal)

* Final angle (~vertical)

Validation condition:



* Angle crosses threshold (e.g. from ~0° → ~90°)

4) Replace Your Validation Logic

Your current:



* ROI intersection %

* QR disappearance timing

This is incomplete.

Replace with a 3-condition state machine:

State 1: TRACKING



* Object continuously tracked (tracker OR motion fallback)

* Confidence maintained

State 2: INSERTION DETECTED

Trigger when:



* Center of object enters slot ROI

* AND velocity vector points toward slot

State 3: DEPOSIT VALIDATED

Only confirm if ALL are true:



1. Inside ROI

   * Bounding box center inside slot region (not just overlap)

2. Orientation change

   * Angle ≈ vertical (from `minAreaRect`)

3. Stability

   * Object stops moving for X frames

4. QR absence (secondary, not primary)

   * QR not detected anymore (optional confirmation)

5) Critical Fixes to Your Current System

❌ Problem 1: Bounding Box Overlap

This fails when rotated.

✔ Fix:



* Use centroid-in-ROI, not overlap %

❌ Problem 2: QR Disappearance

This is unreliable:



* lighting

* occlusion

* angle

✔ Fix:



* Treat QR only as initial anchor, not validation signal

❌ Problem 3: Losing Track During Rotation

✔ Fix: Combine:



1. Tracker (CSRT)

2. Optical flow (Lucas-Kanade)

3. Contour tracking fallback

6) Minimal Practical Pipeline (Do This)



1. Detect QR → get initial bbox

2. Initialize:

   * CSRT tracker

   * ORB descriptors

3. Each frame:

   * Update tracker

   * If confidence drops:

      * Use optical flow OR contour tracking

4. Extract contour → compute:

   * centroid

   * angle (`minAreaRect`)

5. Maintain history:

   * position

   * velocity

   * angle

6. Validate deposit ONLY if:

   * centroid inside slot ROI

   * angle ≈ vertical

   * low movement for ~0.5–1 sec

7) If You Want High-End Robustness

Upgrade path:



* Use YOLOv8 + oriented bounding boxes (OBB)

* Pair with ByteTrack or DeepSORT (angle-aware)

* This removes need for manual angle estimation

Bottom Line

Your current approach is event-based and brittle. You need:



* continuous tracking

* rotation awareness

* state-based validation")
